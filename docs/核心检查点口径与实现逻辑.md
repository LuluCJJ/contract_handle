# 核心检查点口径与实现逻辑

本文记录 2026-05-13 业务复盘后的最新检查口径，重点解决三个问题：检查项围绕业务检查点收敛、证据与结论对齐、减少同类问题重复展示。

## 1. 总体口径

本 demo 的检查不再以“模型发现了多少条风险”为核心，而是以“业务必须关心哪些检查点”为核心。

第一层是电子流已有、材料也应承载的信息。现阶段固定收敛为 8 个必检点：

| 检查点 | 业务含义 | 当前实现 |
| --- | --- | --- |
| 网银平台 | 本次在哪家银行/网银平台办理 | `platform.platform_name / bank_name / branch_name`，不检查平台编号 |
| 操作员身份 | 本次为哪个操作员办理 | `users[].user_name` 与电子流用户对象匹配 |
| 证件号码 | 操作员身份证/护照号码 | OCR 证件与电子流人员池比对，身份证格式复核 |
| 账户名称 | 企业银行账户法定名称 | 支持忽略常见账户性质后缀，处理英文常见缩写 |
| 账户账号 | 企业银行账户号 | 对应电子流 `users[].account_number`，不是平台编号或流程编号 |
| 办理事项 | 开通、变更、注销、加挂等 | A2 语义归一 + B1 场景合理性复核 |
| 权限范围 | 授权、支付、查询、上传四类权限 | 后端拆成四项逐项核对，再由前端聚合展示 |
| 网银介质 | U盾、Token、证书等介质 | 检查介质类型、编号、数量、办理动作 |

第二层是电子流没有、但材料需要关注的信息。当前作为补充检查点：

| 补充检查点 | 业务含义 | 当前实现 |
| --- | --- | --- |
| 填写规范 | 必填项、手机号、工号、限额币种等 | `sop_checker.py` |
| 风险条款/敏感词 | 银行条款或授权表述中的高风险词 | `risk_clause_checker.py` |
| 多文档一致性 | 同一事实在多份材料中是否冲突 | 现有跨文档检查与总结逻辑 |
| 摘要风险 | 从材料摘要看是否存在业务实质风险 | 当前为文档设计口径，后续可产品化 |

## 2. 关键改动

### 2.1 办理事项实质冲突

旧逻辑直接扫描全文，只要 EFlow 为开通且全文出现“注销、取消、Cancel”等词，就可能输出“办理事项实质冲突”。银行制式表格中经常出现说明项、未勾选选项、历史状态或英文模板文字，这会造成批量误报。

新逻辑改为只使用抽取出的场景证据：

```python
scenario_evidence = business_activity + scenario_type + action_type + action_summary + evidence_summary
```

只有当电子流场景与材料抽取场景形成硬冲突时才输出红灯。`MODIFY/维护/更改服务` 不再天然视为与 `OPEN` 冲突，因为很多银行使用“维护/更改服务”表格承载新增用户、加挂介质或新增权限。

端到端验证后又补充了一个确定性兜底：如果 LLM 语义审查仍把“变更/维护模板”与开通/注销判断为硬冲突，后端会将其降级为“模板口径需要确认”，避免在业务页面上形成错误的高风险结论。

### 2.2 网银平台

平台编号不参与检查。当前检查重点是：

1. 如果电子流和材料都能识别银行/平台名称，则做名称归一比对。
2. 如果双方都有分行/支行信息，则追加分行核对。
3. 如果电子流有平台但材料未稳定识别，输出黄灯确认，而不是静默跳过。

提示词也要求模型从标题、表头、页眉、Logo 附近和关键办理位置提取银行信息，同时避免把未选中的银行列表或填写说明误当事实。

平台分行核对已支持常见简称，例如 `工行朝阳支行` 与 `北京朝阳支行` 可归一为同一办理分支。平台代码、渠道代码、系统编号不作为业务检查点输出。

端到端验证后补充了 LLM 噪声过滤：如果确定性检查已能识别平台银行/分行，则过滤 LLM 输出的“平台名称缺失/平台代码缺失”类提示，避免业务页面同一事项一边绿灯、一边黄灯。

### 2.3 账户账号

电子流中的实质账户字段是 `users[].account_number`，业务含义是企业银行账户号。页面和检查明细均按“银行账户账号”表述，不再混同为平台账号、用户账号或流程号。

### 2.4 权限范围

权限不再只输出一个粗粒度 `permission_scope`。后端按四种资金安全相关权限逐项输出：

| 权限 | 含义 |
| --- | --- |
| authorize | 授权、审批、复核、放行 |
| payment | 付款、支付、转账、汇款、制单提交 |
| query | 余额、明细、交易、对账单查询 |
| upload | 文件上传、上载、批量导入 |

如果材料中出现电子流未登记的权限，输出该权限的红灯；如果电子流登记但材料未稳定识别，输出黄灯；一致则绿灯。前端再将这四项聚合为业务用户可读的“权限范围”检查点，避免重复刷屏。

当电子流提供了用户明细时，粗粒度 LLM `permission_scope` 检查会被过滤，避免与四项逐项检查重复。后续如果要保留 LLM 权限能力，应限定为“额外权限/超配权限发现”，而不是再次判断四项基础权限。

### 2.5 介质

介质检查按业务最新口径拆成：

1. 是否申请/新增/加挂/注销介质。
2. 介质类型是否一致，例如 U盾、Token、数字证书。
3. 介质数量是否一致，例如“申请证书 2 张”。
4. 如果电子流或材料存在介质编号，则核对编号。

## 3. 报告检查点模型

当前版本已从“前端临时聚合”改为“后端生成业务检查点”。后端在 `_run_pipeline` 报告封装阶段调用 `check_point_builder.build_check_points()`，把全部底层检查转换成 `AuditReport.check_points`。

```text
hard_checks / semantic_checks / cross_checks
  -> check_point_builder.py
  -> AuditReport.check_points[]
  -> frontend/app.js 渲染
```

这样做的核心目的是让页面不再猜测“哪些规则应该合并”，而是直接消费后端已经整理好的业务检查点。

### 3.1 check_points 结构

| 字段 | 含义 |
| --- | --- |
| `key/title/order` | 检查点标识、业务名称和展示顺序 |
| `traffic_light/severity/business_status` | 红黄绿状态和内部风险等级 |
| `summary/suggestion` | 面向业务用户的结论和建议动作 |
| `source_a_value/source_b_value` | 聚合后的电子流登记信息与材料识别信息 |
| `doc_names` | 涉及材料 |
| `evidence_snippets` | 与该检查点相关的原文/解析片段 |
| `evidence_items` | 底层核对明细，用于解释为什么合并 |

### 3.2 展示原则

聚合后，一条“申请人错配”类问题即使底层来自多份材料、多条规则，也会在页面上收敛为同一个业务检查点。主表不再按申请人、操作员、证件持有人拆成多个身份行，而是统一进入“操作员身份”检查点。

证据弹层分三层展示：

| 层级 | 面向用户的问题 | 展示内容 |
| --- | --- | --- |
| 检查点结论 | 这个检查点结论是什么 | 红黄绿状态、业务化解释、建议动作 |
| 电子流/材料对照 | 系统看到了什么 | 聚合后的电子流登记值、材料识别值，不再显示“2 条底层检查”这类技术占位 |
| 底层核对明细 | 为什么合并、合并了哪几条 | 每条底层核对的名称、状态、电子流值、材料值、依据片段 |

“底层核对 N 项”不是业务结论，而是解释性入口。业务用户可以只看检查点结论；产品和 IT 可以展开证据查看底层规则。

材料原文/解析片段现在优先使用与该检查点相关的 `check.evidence / source_b_value`，再降级使用文档摘要。避免所有检查点都显示同一段文档摘要。

前端仍保留旧报告的兜底聚合函数，但只在后端没有返回 `check_points` 时使用。

## 4. 关键提示词摘录

抽取提示词已补充以下约束：

```text
通篇阅读文档。文档结尾或字段附近的填写说明、选项解释、代码表可用于理解勾选项和字段含义，
但不要把未勾选的说明文字、样例文字、空白模板项当成本次申请事实。

提取本次办理对应的银行/网银平台，不检查平台编号或系统代码。
如果材料中清晰写出总行/主行 + 分行/支行，分别填写 platform.bank_name 与 platform.branch_name。

四个权限必须分别判断，不要因为“权限”两个字泛泛出现就全部置 true。
若出现收款、外汇、贸易融资、理财、全部权限、管理员等四大权限之外或明显过宽的表述，
也保留在 raw_text 中，供后续超配复核。
```

## 5. 下一步建议

1. 让业务确认 8 个必检点的名称是否就是未来页面语言。
2. 为每个必检点准备 3-5 个真实脱敏反例，形成回归样本。
3. 权限超配词库需要继续补充，例如收款、外汇、贸易融资、全部权限、管理员等。
4. 产品化阶段建议把 `users[]` 进一步拆成 `users[].accounts[].activities[].permissions[]`，当前 demo 仍是轻量结构。

## 6. 公司真实样例回归口径补充

2026-05-13 晚间使用公司真实脱敏样例复测后，暴露出三类“看起来很多问题、实质上是口径和数据结构未对齐”的误报。本节记录最新修正口径，后续交接产品和 IT 时应以本节为准。

### 6.1 电子流嵌套账户与介质必须先归一化

公司电子流中账户信息不是平铺在 `users[]` 上，而是放在 `users[].accounts[]` 中；介质信息也可能放在 `users[].media.new_media_type` 等字段中。旧逻辑只读取轻量 demo 里的平铺字段，因此会错误得出“0 个企业账户”“未识别账户”“账户状态缺失”“未涉及介质”的结论。

最新逻辑在进入 `EFlowData` 模型前增加 `_normalize_eflow_payload()`，先把公司电子流归一化为 demo 内部可消费结构：

```text
users[].accounts[].account_number      -> users[].account_number
users[].accounts[].account_name_zh/en  -> users[].account_name / account_name_en
users[].accounts[].account_status      -> users[].account_status
users[].accounts[].permission_scope    -> users[].permission_scope 汇总
users[].media.new_media_type           -> users[].media.media_type
users[].media.is_blank_media           -> users[].media.is_blank
platform.bank_short_name               -> platform.bank_short
platform.platform_url                  -> platform.login_url
```

因此，后续报告中的账户数量、账户名称、账号、权限范围和介质类型，应优先来自归一化后的电子流结构，而不是让 LLM 从材料中反推。

### 6.2 平台编码不是业务检查点

业务已明确：网银平台检查看“在哪家银行/哪个网银平台办理”，不检查 `platform_code`、平台编号、系统编码、渠道编码。旧逻辑虽然在确定性规则里不检查平台编码，但 LLM 语义检查仍可能输出“平台编码缺失”，导致页面出现无意义黄灯。

最新逻辑在语义检查过滤层增加平台编码噪声过滤。凡检查字段、检查名称、原因码或描述中出现以下含义，均不作为业务检查点输出：

```text
platform_code / platform code / 平台编码 / 平台编号 / 平台代码 / 系统编码 / 渠道编码
```

网银平台的有效证据应来自银行名称、平台名称、主行/分行、标题、页眉、表头或业务办理位置，而不是平台代码。

### 6.3 “Cancel/注销”不能直接等于办理事项冲突

银行制式申请表中经常同时出现 open、modify、cancel 等选项或说明文字。如果全文扫描只命中 `Cancel`，但结构化语义已经识别为“开通/新增/OPEN”，不应直接输出“办理事项实质冲突”。

最新逻辑做两层修正：

1. SOP 场景识别对 open/cancel/modify 命中进行计数。当开通证据不少于注销证据时，优先认定为开通场景。
2. 检查点证据聚合时，如果同一个检查点同时有红/黄异常和绿灯底层核对，业务侧只展示红/黄对应的活跃证据；绿灯底层核对不再混入异常证据区，避免出现“结论说冲突，证据又说开通一致”的自相矛盾展示。

### 6.4 账户状态缺失不应作为当前核心噪声输出

账户状态是电子流账户对象中的重要辅助字段，但在当前“八大检查点”里，账户状态不是独立必检点。若电子流和材料双方都没有稳定提供账户状态，系统不应单独生成“账户信息需要复核”的业务提示；只有当电子流已明确账户状态异常，或后续业务确认账户状态要纳入必检点时，再升级为正式检查。

最新语义过滤层会跳过账户状态缺失类提示，避免它挤占审核人的注意力。

### 6.5 介质注销类提示在开通场景下默认过滤

开通场景下，如果系统和文档都未标记“注销介质”，这不是不一致，也不是风险。旧逻辑曾把“无需注销介质，状态一致”错误放入红灯区。最新过滤层会在开通场景下跳过注销/取消介质类提示，除非材料明确出现与本次开通相冲突的注销事实。

### 6.6 身份类仍需业务补充别名/拼音映射

真实样例中，电子流可能登记为“拼音姓名 + 工号”，材料或证件识别为中文姓名。这不是简单字符串一致问题，而是中文姓名、拼音、工号之间的映射问题。当前系统会把此类情况收敛到“操作员身份”一个检查点下，并保留为审核人确认，不再拆成多条刷屏。

后续若要减少该类黄灯，需要产品侧明确至少一种补充机制：

1. 电子流同步员工中文名、英文名、工号三元组。
2. 接入员工主数据，按工号回查中英文姓名。
3. 建立业务配置型姓名别名表，经业务确认后生效。
4. 对中文名转拼音做辅助匹配，但仍需防止重名和拼写差异导致误判。
