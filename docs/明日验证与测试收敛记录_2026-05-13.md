# 明日验证与测试收敛记录

**时间**：2026-05-13 凌晨

**目标**：把检查结果从“风险条目堆叠”收敛为“业务检查点结论”，并通过测试用例刷新和端到端验证，减少误报、重复提示和证据错位。

## 1. 今晚形成的判断

当前版本应优先满足三个目标：

1. 检查内容围绕业务必检点，而不是围绕模型随手发现的风险条目。
2. 每个检查点只输出一个主结论，底层多条检查可以合并，但不能在页面上互相打架。
3. 端到端验证时，不仅看流程是否跑通，还要看检查点、证据、源头字段是否对得上。

## 2. 已收敛的检查点

第一层：电子流已有、材料应承载的信息。

| 检查点 | 当前口径 |
| --- | --- |
| 网银平台 | 不看平台编号；核对银行/平台名称，能识别分行时核对分行 |
| 操作员身份 | 多用户逐对象匹配，不再把多人合成一个人 |
| 证件号码 | OCR 证件与电子流人员池比对，身份证格式和有效期复核 |
| 账户名称 | 核对账户法定名称，支持常见账户性质后缀和英文缩写归一 |
| 账户账号 | 对应电子流 `users[].account_number`，业务含义为银行账户号 |
| 办理事项 | `OPEN / CANCEL / MODIFY` 分层判断；维护/变更模板不直接视为方向相反 |
| 权限范围 | 拆为授权、支付、查询、上传四项逐项检查 |
| 网银介质 | 检查介质类型、编号、数量、办理动作；动作检查必须有介质事实支撑 |

第二层：电子流没有、但材料需要关注的信息。

| 检查点 | 当前口径 |
| --- | --- |
| 填写规范 | 必填项、占位符、手机号、工号、限额币种等 |
| 风险条款 | 敏感词/高风险条款提示 |
| 多文档一致性 | 跨材料同一事实是否冲突 |
| 摘要风险 | 仍处于方案设计阶段，后续需业务确认风险清单 |

## 3. 今晚发现并修正的问题

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| 开通/申请类材料被误判为注销 | B1 曾扫描全文反向词，模板标题/说明中的“注销/Cancel”会误伤 | 改为只基于结构化场景证据判断，并尊重显式 `MODIFY` |
| LLM 把“变更/维护模板”与开通冲突 | 银行模板名称和实际办理动作不是一回事 | 增加确定性兜底，将此类检查降级为“模板口径需要确认” |
| 网银平台证据错位 | 原来平台检查挂在 `account` 字段簇 | 改为 `platform` 字段簇，并支持分行简称归一 |
| 平台代码缺失被提示 | 业务明确平台编号不检查 | 过滤 LLM 的平台代码/系统编号类提示 |
| 权限范围重复刷屏 | A2 先做整体权限集合，再 A1 做用户级权限 | 当电子流有用户明细时，过滤粗粒度 LLM `permission_scope` 检查 |
| 介质动作误报 | 只有动作词，没有介质类型/编号/数量等事实 | 介质动作检查增加事实门槛 |
| 多用户 case 口径过旧 | “制单员”在新口径下属于支付相关动作，但测试电子流写成 `payment=false` | 刷新 `case_015_boc_multi_pass` 电子流和多用户单测 |

## 5. 明天建议重点看

1. 页面上是否已经从“风险列表”变成“检查点列表”。
2. 每个红/黄灯是否能对应一个明确检查点，而不是同类问题重复出现。
3. 权限范围是否能按授权、支付、查询、上传理解，不再出现“全部权限一起打包”的模糊结论。
4. 平台和账号证据是否对得上：平台看银行/分行，账号看银行账户账号。
5. OCR 证件样本与电子流人员池是否需要重新准备，避免测试样本本身制造黄灯。

## 6. 仍需真实样本继续验证

1. 不同银行“维护/变更/签约维护”模板下，哪些勾选项应视为新增、注销、加挂或保留。
2. “制单员/经办员/录入员/提交人”等角色是否全部归入支付权限，需业务确认。
3. 介质数量、介质编号在不同模板中的表达差异。
4. 多账号、多用户、多活动同时出现时，是否需要从当前 `users[]` 进一步拆成 `users[].accounts[].activities[]`。
5. 风险条款和摘要风险的业务优先级，需要明天继续和业务确认。

## 7. 公司样例追加复测结论

晚间公司样例暴露的问题，核心不是前端单纯展示问题，而是上游三处输入口径未对齐：

| 现象 | 根因 | 已修正 |
| --- | --- | --- |
| 最终报告显示 0 个企业账户、未识别账户、账户状态缺失 | 公司电子流账户在 `users[].accounts[]`，旧 demo 只吃平铺字段 | 在 `_parse_eflow_v3` 前增加电子流归一化，合并嵌套账户、账户状态、权限范围、介质类型 |
| 网银平台提示平台编码缺失 | 平台编码不是业务检查点，但 LLM 语义检查仍输出了编码缺失 | 过滤 `platform_code/平台编码/编号/代码/系统编码/渠道编码` 类提示 |
| 办理事项把模板里的 Cancel 当成注销事实 | 制式表格存在 open/cancel/modify 选项，旧逻辑对反向词过敏 | SOP 场景识别按命中计数，并让检查点只展示红/黄活跃证据，不混入绿灯底层证据 |
| 开通场景下出现介质注销类红灯 | “无需注销介质、状态一致”被错误当作异常 | 开通场景默认过滤注销/取消介质类噪声 |
| 操作员身份仍需确认 | 电子流是拼音+工号，材料/OCR 是中文姓名或证件号 | 当前收敛为一个“操作员身份”检查点；后续需要员工主数据或别名表降低黄灯 |
