# Agentic 升级思考笔记

> 当前状态：一条由 8 个固定步骤构成的线性 Pipeline。
> 目标：识别哪些地方可以植入"自主判断 → 动态调整 → 自我修正"能力。

---

## 一、当前 Pipeline 结构回顾

```
上传材料 → 解析 EFlow → 解析文档 → OCR 证件
        → 硬比对 → 语义分析 → 全局综述 → 返回报告
```

问题：每一步输入/输出都是固定的，LLM 只在"语义分析"和"全局综述"这两个末端节点参与，且**无法回头**影响之前的步骤。

---

## 二、三个最有价值的 Agentic 改造点

### 🔁 改造点 A：解析层 — 自修正解析循环

**当前**：文档解析和 OCR 提取是一次性的，输出质量参差不齐，结果差了也没人知道。

**Agentic 化思路**：在解析完成后，增加一个"质量仲裁者"步骤。

```
解析文档 → [质量仲裁 Agent]
                ↓ 判断"可信度"
         高置信 → 继续正常流程
         低置信 → 策略切换（换提示词、换方法重试）→ 再次判断
```

**核心机制**：
- LLM 扮演"自我审查者"：检查提取出的字段是否在语义上自洽（如：公司名称和证件号能否对上）
- 若发现内部矛盾，自动触发"二次提取"并合并两次结果取置信最高项
- 最多 2 次重试，超过则标记为"待人工核查"

**价值**：这是提升提取质量最直接的 Agentic 改造，对后续所有比对步骤至关重要。

---

### 🔎 改造点 B：审计层 — 风险追踪代理（Risk Drilldown Agent）

**当前**：发现一个 MISMATCH 就输出一条 CheckResult，不做进一步追问。

**Agentic 化思路**：引入"风险追踪代理"，对每一个 CRITICAL 级别的发现，自动展开追问。

```
硬比对发现 CRITICAL 风险
    ↓
[风险追踪 Agent] 接管该风险点
    ↓
生成 2-3 个追问子任务：
  - "是笔误还是意图篡改？"（数字形近 → 低风险，字符完全不同 → 高风险）
  - "涉及的账号在其他文档里有没有被提到？"（跨文档比对）
  - "EFlow 里的审批路径上有没有涉及该账号的人员？"（权限链路核查）
    ↓
汇总成"风险评分 + 核查说明"
```

**价值**：
- 目前只有"发现不一致"，但**为什么不一致、风险等级是否准确**完全依赖人工判断
- 加入追踪代理后，系统可以输出"这很可能是笔误（低风险）"或"这两个账号在 EFlow 中归属不同事业部（高风险）"的差异化结论

---

### 📚 改造点 C：知识层 — 审计规则自学习（Rule Accumulation Loop）

这是您提到的第二个问题的核心。

**当前**：规则固化在 `hard_comparator.py` 和 `prompts.json` 中，只能人工修改。

**Agentic 化思路**：建立一个"规则观察者"旁路。

```
每次审计完成后：
    [规则观察者 Agent] 分析本次报告
        ↓
识别：
  "有 N 次，系统没有标记但人工后来标了的情况" → 候选新规则
  "有 N 次，系统标了但人工复核是误报的情况" → 候选删除规则
        ↓
将候选规则写入"规则草稿库"（rule_candidates.json）
        ↓
定期由人工或 LLM 聚合器审阅：
  批准 → 进入正式规则库（rules.json）
  驳回 → 打上标签留档
```

**关键设计**：
- **不让 AI 直接修改规则库**（风险过高），而是走"提案-审阅"的两段式流程
- 人工审阅界面可以直接在现有的前端 Dashboard 里做：侧边多一个"规则草稿" Tab

## 三、实现优先级推荐

| 改造点 | 技术风险 | 业务价值 | 推荐优先级 |
|---|---|---|---|
| A - 解析自修正循环 | 低（在已有逻辑上加一层） | 高（提升所有后续环节的数据质量） | ⭐⭐⭐ 最高 |
| B - 风险追踪代理 | 中（需设计多轮对话协议） | 极高（审计深度质的提升） | ⭐⭐ 次高 |
| C - 规则自学习 | 中低（需配合简单存储和 UI）| 高（系统持续成长的核心能力） | ⭐⭐ 次高 |

## 四、三者如何协同

```
                  ┌──────────────────────────────────────┐
                  │           Agentic Audit Loop         │
                  │                                      │
  上传材料 ──→ [A: 自修正解析] ──→ 比对 ──→ [B: 风险追踪] ──→ 最终报告
                                                  │
                                                  ↓
                                        [C: 规则观察者]
                                                  │
                                           rule_candidates
                                                  │
                                         ← 人工审阅 / LLM 聚合
                                                  │
                                           rules.json (更新)
                                                  │
                                         下次审计时生效 ──────→
```

## 五、一个值得深入讨论的设计问题

**规则的形态是什么？**

目前的"规则"分两类：
- **硬规则**：字符精确匹配（代码实现，在 `hard_comparator.py`）
- **软规则**：语义提示词（文本，在 `prompts.json`）

如果要让规则可以动态积累，需要明确**规则存储格式**。建议的候选结构：

```json
{
  "rule_id": "R-024",
  "type": "soft",
  "trigger": "当操作员权限为支付且账号为对公账号时",
  "instruction": "需要特别核查法定代表人是否与申请人一致",
  "source": "audit_20260416 (人工发现)",
  "status": "candidate",
  "approved_by": null
}
```

这种结构的软规则可以在每次语义分析时动态拼接到 prompt 中，实现"规则代码化"的效果。
