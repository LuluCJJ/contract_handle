# 作业规范与摘要风险设计

**文档定位**：用于和业务确认“电子流没有、但文档仍需关注”的风险类型与检查口径。

**更新时间**：2026-05-12

**适用范围**：银行通道/网银权限申请、变更、注销等材料预审场景。

---

## 1. 设计边界

这部分不是检查电子流字段是否一致，而是回答：

> 即使电子流没有明确字段，材料自身是否存在会影响银行办理质量、对外表达准确性或审核人判断的风险？

因此它不能被设计成“AI 通篇找茬”。更稳妥的方式是：

```text
文档解析
→ 结构化事实抽取
→ 单文档摘要
→ 多文档摘要归并
→ 基于业务 Playbook 的有限风险判断
→ 输出风险类型、原文依据、审核建议
```

当前建议分为两块：

1. 风险条款/敏感词：短期可以快速落地，命中即提示审核人重点关注。
2. 作业规范/摘要风险：长期逐步补充，需要业务确认风险清单、样例和处置口径。

---

## 2. 摘要风险的核心思想

摘要不是为了“写得好看”，而是为了让 AI 把一份文档压缩成可检查的业务事实。

每份文档摘要建议包含：

| 摘要字段 | 说明 | 示例 |
| --- | --- | --- |
| 文档类型 | 申请表、授权书、介质申请表、身份证件、补充协议等 | 企业网银操作员申请表 |
| 办理事项 | 文档声称办理开通、变更、注销、加挂等 | 新增操作员并开通查询权限 |
| 涉及主体 | 公司、申请人、操作员、授权人、法人、联系人 | Liu Yang、Wang Fang |
| 涉及账户 | 账户名称、账号、开户行、平台 | 上海星辰国际贸易有限公司，账号尾号 3456 |
| 涉及权限 | 授权、支付、查询、上载及其他权限 | 查询、转账、复核 |
| 涉及介质 | U盾、Token、证书、数量、编号、是否加挂/注销 | 新增 2 个 U 盾 |
| 异常表述 | 风险词、过宽授权、前后冲突、空白字段 | 全部权限、长期有效 |
| 证据片段 | 能支撑摘要判断的原文 | “授权办理网银相关全部事项” |

整套材料摘要建议包含：

| 汇总字段 | 说明 |
| --- | --- |
| 本次材料共同指向的办理事项 | 多份材料是否都指向同一业务活动 |
| 关键对象闭环情况 | 人、账户、权限、介质是否能一一对应 |
| 多文档一致性 | 公司、法人、联系人、账号、权限、介质表述是否冲突 |
| 风险提示 | 是否出现敏感词、过宽授权、职责冲突、注销不完整等 |
| 审核建议 | 需要审核人优先看的事项 |

## 3. 风险类型总览

| 风险大类 | 适合短期落地吗 | 主要判断依据 | 推荐输出 |
| --- | --- | --- | --- |
| 填写规范风险 | 是 | 字段、格式、空白、勾选项 | 黄灯或红灯 |
| 多文档一致性风险 | 部分适合 | 多文档摘要和抽取事实 | 黄灯为主 |
| 业务实质风险 | 需要逐步沉淀 | 摘要 + 业务 Playbook + 原文证据 | 黄灯或红灯 |
| 风险条款/敏感词 | 是 | 词库 + 上下文片段 | 红灯或黄灯 |
| 审核链路风险 | 中期适合 | 人员角色、权限组合、授权链条 | 黄灯为主 |
| 注销/变更完整性风险 | 中期适合 | 注销对象、介质、权限、账号保留情况 | 黄灯或红灯 |

---

## 4. 填写规范风险

这类风险最适合规则化，目标是发现材料是否“填得完整、格式合理、没有自相矛盾”。

| 风险类型 | 摘要中可能发现什么 | 示例 | 建议等级 | 是否需业务确认 |
| --- | --- | --- | --- | --- |
| 必填项缺失 | 必填栏目为空、待填、N/A、TBD、XXX | 申请人姓名为空；联系人电话未填写 | 黄灯 | 是 |
| 字段格式异常 | 日期、证件号、手机号、账号、金额不符合基础格式 | 身份证号不足 18 位；日期为 2026/13/40 | 黄灯 | 是 |
| 勾选和正文冲突 | 表格勾选项与正文说明不一致 | 勾选“注销”，正文写“新增操作员” | 红灯 | 是 |
| 金额/限额缺单位 | 摘要有金额但缺币种或单位 | 日限额 500000，未写人民币/美元 | 黄灯 | 是 |
| 签章/日期缺失 | 文档摘要显示签名、盖章、日期缺失 | 授权人签字栏为空 | 黄灯 | 是 |
| 模板版本不适配 | 文件类型和办理事项不匹配 | 用开户表办理网银权限注销 | 黄灯 | 是 |
| 字段填写位置异常 | 信息写在备注或非标准栏目 | 账号写在备注栏，不在账号栏 | 黄灯 | 待确认 |
| 手写/涂改风险 | 摘要或 OCR 识别到涂改、划线、手写补充 | 账号附近有手写修改痕迹 | 黄灯 | 待确认 |

业务确认重点：

- 哪些字段属于必须检查的必填项？
- 哪些字段缺失应提示“建议补充”，哪些只需要“审核人确认”？
- 格式异常是否只提示，不做错误判断？

## 5. 多文档一致性风险

这类风险不一定依赖电子流。它关注同一套材料内部是否讲的是同一件事。

| 风险类型 | 摘要中可能发现什么 | 示例 | 建议等级 | 是否需业务确认 |
| --- | --- | --- | --- | --- |
| 公司主体不一致 | 多份文件的公司名称或证件号不同 | 主表为 A 公司，授权书为 B 公司 | 红灯 | 是 |
| 法人信息不一致 | 不同文件提到的法人姓名不同 | A 表写 Wang Wei，B 表写 Wang Way | 黄灯 | 是 |
| 联系人/申请人不一致 | 申请人、联系人、经办人表述冲突 | 主表申请人为 Liu Yang，附件经办人为 Wang Jun | 黄灯 | 是 |
| 账户对象不一致 | 账号、户名、开户行、平台跨文件不一致 | 主表账号尾号 3456，附件尾号 7890 | 红灯 | 是 |
| 业务动作不一致 | 同套材料同时出现开通、注销、变更 | 主表开通，授权书写撤销原权限 | 红灯 | 是 |
| 权限描述不一致 | 不同文件对同一人权限描述不同 | 主表仅查询，附件写查询及转账 | 红灯 | 是 |
| 介质处理不一致 | 一处申请新增介质，一处沿用原介质 | 新增 U 盾，同时写不更换原介质 | 黄灯 | 是 |
| 人员数量不一致 | 主表多名操作员，但证件或授权文件不足 | 两名操作员只上传一张身份证件 | 黄灯 | 是 |
| 附件归属不清 | 附件无法关联到具体申请事项或人员 | 授权书未写授权给哪个操作员 | 黄灯 | 是 |

业务确认重点：

- 法人、联系人这类非核心电子流字段，是否只要“提示复核”？
- 多文档一致性是否优先检查公司、账号、权限、介质四类？
- 附件归属不清是否作为独立风险类型？

## 6. 业务实质风险

这类风险最需要业务 Playbook。它不是简单字段错，而是从业务含义上判断“这套材料是否可能让银行误办、错办或超范围办理”。

| 风险类型 | 摘要中可能发现什么 | 示例 | 建议等级 | 是否需业务确认 |
| --- | --- | --- | --- | --- |
| 权限超配 | 角色实际需要低权限，但材料出现高权限 | 制单员同时申请支付和授权 | 红灯 | 是 |
| 职责冲突 | 同一人同时承担制单、复核、授权 | 同一操作员具备录入和审批权限 | 红灯 | 是 |
| 业务范围过宽 | 材料表述超出本次办理事项 | 授权办理网银相关全部事项 | 黄灯/红灯 | 是 |
| 注销不完整 | 注销用户但未说明权限、介质是否同步处理 | 注销操作员，未提 Token 是否回收 | 黄灯 | 是 |
| 权限保留不当 | 注销/变更场景中出现保留原权限 | 注销用户但附件写原权限继续有效 | 红灯 | 是 |
| 加挂对象不清 | 介质、权限或账户加挂对象不明确 | 申请加挂 U 盾，但未说明给谁 | 黄灯 | 是 |
| 介质数量异常 | 介质数量与人员或权限关系不合理 | 一个操作员申请 3 个 U 盾 | 黄灯 | 是 |
| 授权链条缺失 | 涉及支付/授权但未体现复核或授权链条 | 申请支付权限，但无复核授权人 | 黄灯 | 待确认 |
| 高风险权限组合 | 支付、授权、上传等组合超过业务需要 | 同一人支付 + 授权 + 上载 | 红灯 | 是 |
| 业务场景混杂 | 材料同时办理多个不清晰活动 | 开通、注销、变更都出现，但无清晰对象 | 黄灯/红灯 | 是 |

业务确认重点：

- 哪些权限组合一定是高风险？
- 哪些角色不应拥有支付或授权？
- 介质数量与人员数量是否有明确约束？
- “全部事项”“所有权限”等过宽表述是否一律提示？

## 7. 风险条款/敏感词

这类风险和银行表单字段关系不大，更多是对外文书条款和补充协议中的风险表达。

| 风险类型 | 敏感词示例 | 关注点 | 建议等级 |
| --- | --- | --- | --- |
| 责任扩大 | 无限连带责任、全部责任、无条件、不可抗辩 | 是否扩大公司责任 | 红灯 |
| 权限长期化 | 自动续期、自动顺延、长期有效 | 是否造成权限长期有效 | 黄灯/红灯 |
| 通知义务弱化 | 无需另行通知 | 银行变更是否无需通知 | 黄灯 |
| 银行单方权利 | 银行单方变更权限、单方终止协议、单方调整费率 | 是否赋予银行单方处理权 | 红灯 |
| 免责条款 | 银行不承担任何责任 | 是否存在不合理免责 | 黄灯/红灯 |
| 最终解释权 | 最终解释权归银行所有 | 是否影响争议处理 | 黄灯 |

短期实现建议：

- 使用词库扫描。
- 命中后展示上下文片段。
- 不直接判定不能接受，只提示“请重点审核该条款”。

## 8. 摘要风险判断模板

单文档摘要可使用如下结构：

```json
{
  "doc_name": "bank_app.docx",
  "doc_type": "银行申请表",
  "declared_activity": "新增操作员并开通查询权限",
  "subjects": ["上海星辰国际贸易有限公司", "Liu Yang"],
  "accounts": ["454676800100123456"],
  "permissions": ["查询"],
  "media": ["U盾 1 个"],
  "risk_phrases": [],
  "unclear_points": ["未说明介质编号"],
  "evidence": ["文档第 X 段出现新增操作员和查询权限"]
}
```

整套材料风险判断可使用如下结构：

```json
{
  "overall_activity": "为 Liu Yang 开通查询权限并绑定账号 3456",
  "object_closure": "人员、账号和权限可关联；介质编号缺失",
  "cross_document_conflicts": [],
  "risk_items": [
    {
      "risk_type": "介质信息不完整",
      "risk_level": "YELLOW",
      "reason": "申请介质但未说明介质编号或持有人",
      "evidence": "介质申请表仅写新增 U 盾"
    }
  ]
}
```

## 9. 示例

### 示例一：权限超配

电子流摘要：

```text
为 Liu Yang 在中国银行企业网银下开通查询权限，绑定账号 A。
```

文档摘要：

```text
主申请表新增操作员 Liu Yang，权限为查询、转账。
授权书授权 Liu Yang 办理网银相关全部事项。
```

建议输出：

| 风险 | 说明 | 依据 | 建议 |
| --- | --- | --- | --- |
| 权限范围可能超出本次业务需要 | 电子流为查询，材料出现转账 | “权限为查询、转账” | 建议审核人确认是否应包含支付/转账权限 |
| 授权范围表述过宽 | 授权书写“全部事项” | “网银相关全部事项” | 建议确认授权书是否需要限定本次办理事项 |

### 示例二：注销不完整

电子流摘要：

```text
注销 Wang Fang 的网银操作员权限，系统显示其持有 Token。
```

文档摘要：

```text
申请注销 Wang Fang 操作员，但未提及 Token 是否注销或回收。
```

建议输出：

| 风险 | 说明 | 依据 | 建议 |
| --- | --- | --- | --- |
| 介质处理不完整 | 注销人员但未说明 Token 是否处理 | “注销操作员”且无介质说明 | 建议审核人确认介质是否需同步注销、回收或保留 |

### 示例三：多文档主体不一致

文档摘要：

```text
申请表公司为上海星辰国际贸易有限公司。
授权书公司为上海星辰贸易有限公司。
```

建议输出：

| 风险 | 说明 | 依据 | 建议 |
| --- | --- | --- | --- |
| 公司主体表述不一致 | 两份材料公司名称不同 | 申请表和授权书公司名称不同 | 建议确认是否为简称、旧名称或填写错误 |

## 10. 业务确认清单

明天和业务确认时，可以按以下问题收口：

1. 哪些填写规范风险需要短期纳入 demo？
2. 哪些风险只提示，不作为“发现不一致”？
3. 哪些权限组合必须被认为是高风险？
4. 哪些字段跨文档不一致需要提示？
5. 法人、联系人、经办人这类非核心字段是否只做摘要提示？
6. 风险词命中后是否全部红灯，还是部分黄灯？
7. 摘要风险是否只在报告总结中展示，不进入逐条检查明细？
8. 是否需要区分“业务风险”“材料填写风险”“条款风险”三类展示？

## 11. 业界参考观察

从合同审查、KYC 和文档 AI 的公开实践看，较稳定的做法不是让模型直接自由判断，而是：

- 先做结构化抽取。
- 再做条款/片段级分类。
- 风险判断必须引用原文依据。
- 高风险事项输出 plain-language summary。
- 人类审核人保留最终判断。
